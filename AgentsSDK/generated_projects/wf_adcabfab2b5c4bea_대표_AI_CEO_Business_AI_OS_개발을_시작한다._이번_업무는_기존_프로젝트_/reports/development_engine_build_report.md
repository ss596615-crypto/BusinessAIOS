# Development Engine 구축 보고서

## 1. 목표
대표 AI CEO Business AI OS가 회의실에서 개발 업무를 직접 수행할 수 있도록 Development Engine을 구축한다.

대표 지시 유형:
- 오류 수정
- 기능 추가
- 기능 수정
- 새 기능 생성

대응 절차:
1. 기존 프로젝트 검색
2. GitHub 최신 프로젝트 검색
3. 관련 Python 파일 검색
4. 함수·클래스 분석
5. 수정 대상 결정
6. Worker 배정
7. 실제 코드 수정
8. 자동 테스트
9. 테스트 실패 시 재수정
10. Git Commit
11. 대표 승인
12. Git Push

## 2. 설계 원칙
- 기존 CEO / Workflow / Dashboard / Worker 구조를 유지한다.
- 신규 생성보다 기존 코드 수정을 우선한다.
- 검색 → 분석 → 수정 → 테스트 → 재수정의 반복 루프를 기본 단위로 둔다.
- 모든 작업은 작업 추적 가능한 상태로 기록한다.

## 3. 핵심 기능 정의
### 3.1 기존 프로젝트 검색
- 현재 저장소의 관련 폴더와 파일을 우선 탐색한다.
- 기존 구현, 유사 기능, 재사용 가능한 컴포넌트를 먼저 찾는다.

### 3.2 GitHub 최신 프로젝트 검색
- 외부 권한이 있을 때 GitHub 최신 레포지토리/브랜치/커밋을 조회한다.
- 최신 구현 패턴과 비교하여 현재 프로젝트에 반영 가능성을 검토한다.

### 3.3 관련 Python 파일 검색
- 변경 대상 키워드와 기능 영역을 기준으로 Python 파일을 선별한다.
- 클래스/함수 단위로 책임 범위를 식별한다.

### 3.4 함수·클래스 분석
- 각 파일의 함수와 클래스 역할을 분석한다.
- 의존성과 호출 경로를 확인해 최소 수정 범위를 산정한다.

### 3.5 수정 대상 결정
- 신규 생성보다 기존 함수 수정 우선.
- 변경 영향도가 낮고 재사용 가능한 위치를 우선 선택한다.

### 3.6 Worker 배정
- 분석, 구현, 테스트를 분리해 Worker에 배정한다.
- 구현 Worker는 실제 코드 수정에 집중한다.

### 3.7 실제 코드 수정
- 분석 결과에 따라 코드 반영.
- 공통 로직, 라우팅, 처리기, 서비스 계층을 우선 수정한다.

### 3.8 자동 테스트
- 단위 테스트 / 통합 테스트 / 정적 검사 가능 시 자동 실행.
- 실패 시 원인 기록 후 수정 루프로 되돌린다.

### 3.9 테스트 실패 시 재수정
- 실패 메시지와 스택트레이스를 바탕으로 최소 수정.
- 재실행 후 통과 여부를 기록한다.

### 3.10 Git Commit
- 변경 사항을 명확한 메시지로 커밋한다.
- 커밋 메시지는 작업 목적과 범위를 드러내야 한다.

### 3.11 대표 승인
- push 전 대표 승인 대기 상태를 둔다.
- 승인 없이는 원격 반영을 진행하지 않는다.

### 3.12 Git Push
- 승인 완료 후 원격 저장소에 반영한다.

## 4. 운영 플로우
1. 대표 지시 수신
2. 기존 프로젝트 및 GitHub 최신 정보 검색
3. Python 파일/함수/클래스 분석
4. 수정 대상 확정
5. Worker 배정
6. 코드 수정
7. 자동 테스트
8. 실패 시 재수정 반복
9. Git Commit 생성
10. 대표 승인 대기
11. 승인 후 Git Push

## 5. 유지 대상 구조
다음 기존 구조는 유지한다.
- CEO
- Workflow
- Dashboard
- Worker

추가되는 Development Engine은 위 구조를 대체하지 않고, 실행 오케스트레이션 계층으로 동작한다.

## 6. 구현 권장사항
- 작업 추적용 상태 객체를 도입한다.
- 검색 결과 / 분석 결과 / 수정 계획 / 테스트 결과를 모두 로그화한다.
- 실패 복구를 위한 재시도 메커니즘을 둔다.
- 커밋/푸시는 권한 기반 단계로 분리한다.

## 7. 권한 필요 지점
외부 서비스 권한이 필요한 경우:
- GitHub 조회 권한
- GitHub push 권한
- 배포/CI 권한
- 외부 저장소 접근 권한

## 8. 결론
본 Development Engine은 기존 Business AI OS의 역할 구조를 유지하면서, 대표의 개발 지시를 실제 코드 변경과 검증, 커밋, 승인, 푸시까지 연결하는 실행형 백엔드 흐름으로 설계되어야 한다. 신규 앱 생성이 아니라 기존 코드 기반의 수정 우선 원칙으로 운영하는 것이 핵심이다.
