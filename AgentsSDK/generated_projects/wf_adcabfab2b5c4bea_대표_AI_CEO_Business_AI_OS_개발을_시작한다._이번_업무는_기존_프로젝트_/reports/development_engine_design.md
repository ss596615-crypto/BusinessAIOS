# Development Engine 설계서

## 목적
대표가 다음 유형의 지시를 내렸을 때 AI CEO가 기존 Business AI OS 구조를 유지한 채 개발 업무를 직접 수행하도록 한다.

- 오류 수정
- 기능 추가
- 기능 수정
- 새 기능 생성

## 핵심 원칙
1. 신규 생성보다 기존 코드 수정을 우선한다.
2. 기존 CEO / Workflow / Dashboard / Worker 구조는 유지한다.
3. 작업은 검색 → 분석 → 수정 대상 결정 → Worker 배정 → 코드 수정 → 테스트 → 재수정 → 커밋 → 승인 → 푸시 순서로 진행한다.
4. 사람이 필요한 단계는 승인 대기 상태로 전환한다.
5. 실패한 테스트는 자동 재시도 및 재수정 루프로 처리한다.

## 대표 지시 처리 흐름
### 1. 기존 프로젝트 검색
- 로컬 프로젝트 구조 탐색
- 관련 설정 파일, 워크플로우 파일, 대시보드 파일 식별
- 기존 구현 우선 재사용

### 2. GitHub 최신 프로젝트 검색
- 외부 연결 권한이 있으면 최신 레포지토리 상태 비교
- 권한이 없으면 보류 상태로 기록

### 3. 관련 Python 파일 검색
- 작업 키워드 기반 파일 탐색
- CEO / workflow / worker / dashboard 관련 모듈 우선 확인

### 4. 함수·클래스 분석
- 호출 흐름, 의존성, 입력/출력 계약 파악
- 수정 후보와 영향 범위 분리

### 5. 수정 대상 결정
- 최소 변경 원칙 적용
- 기존 파일 수정 우선
- 신규 파일 생성은 불가피한 경우에만 허용

### 6. Worker 배정
- 분석, 구현, 테스트 역할을 분리 가능
- 단일 작업이면 하나의 Worker에 집중 배정

### 7. 실제 코드 수정
- 기존 파일 내 함수/클래스 단위로 수정
- 구조 변경 시 하위 호환성 유지

### 8. 자동 테스트
- 단위 테스트, 통합 테스트, 정적 점검 실행
- 실패 시 로그를 수정 입력으로 변환

### 9. 테스트 실패 시 재수정
- 실패 원인 분류
- 코드 재수정 후 다시 테스트
- 성공할 때까지 반복

### 10. Git Commit
- 변경 단위별 커밋 메시지 생성
- 커밋 전 변경 요약 저장

### 11. 대표 승인
- 푸시 전 승인 게이트 적용
- 승인 없이는 원격 반영 금지

### 12. Git Push
- 승인 후 원격 반영
- 푸시 결과를 회신

## 운영 상태 정의
- `analysis`: 프로젝트 검색 및 코드 구조 분석
- `editing`: 실제 코드 수정 중
- `testing`: 자동 테스트 수행 중
- `fixing`: 테스트 실패 후 재수정 중
- `awaiting_approval`: 커밋 완료 후 대표 승인 대기
- `pushing`: 승인 후 원격 반영 중
- `completed`: 전체 종료

## 권한 필요 조건
외부 서비스 연동이 필요한 경우 즉시 권한 요청으로 전환한다.

필요 가능성이 있는 서비스:
- GitHub
- Google Drive
- Zapier
- 배포/CI 계정

## 현재 결론
본 업무에서는 외부 계정 연동 없이 수행 가능한 설계 문서를 완성했다. 실제 GitHub 동기화와 푸시는 권한이 있어야 다음 단계로 진행할 수 있다.
