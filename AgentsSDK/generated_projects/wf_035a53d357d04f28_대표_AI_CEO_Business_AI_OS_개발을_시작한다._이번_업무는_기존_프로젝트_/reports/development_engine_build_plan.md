# Development Engine 구축 보고서

## 목표
대표가 다음과 같은 개발 지시를 내리면 Business AI OS가 회의실에서 기존 프로젝트를 수정 중심으로 직접 수행하도록 한다.

- 오류 수정
- 기능 추가
- 기능 수정
- 새 기능 생성

## 요구 동작
1. 기존 프로젝트 검색
2. GitHub 최신 프로젝트 검색
3. 관련 Python 파일 검색
4. 함수·클래스 분석
5. 수정 대상 결정
6. Worker 배정
7. 실제 코드 수정
8. 자동 테스트
9. 테스트 실패 시 재수정
10. Git Commit
11. 대표 승인 대기
12. Git Push

## 설계 원칙
- 신규 생성보다 기존 코드 수정을 우선한다.
- 기존 CEO / Workflow / Dashboard / Worker 구조는 유지한다.
- 모든 실행 단계는 추적 가능해야 한다.
- 외부 권한이 필요한 단계(GitHub, Git Push)는 승인 전까지 대기 상태로 표시한다.

## 운영 흐름
### 1) 지시 접수
대표의 자연어 지시를 분류한다.
- 버그 수정
- 기능 추가
- 기능 수정
- 신규 기능 생성

### 2) 저장소/코드 탐색
- 로컬 프로젝트 구조 탐색
- Python 파일 식별
- 함수/클래스 인덱싱
- GitHub 최신 상태 비교(권한 필요 시 대기)

### 3) 수정 대상 결정
- 영향 범위 분석
- 기존 구조 유지 여부 확인
- 최소 변경안 우선 선택

### 4) Worker 배정
권장 역할:
- 분석 Worker: 파일/함수/클래스 조사
- 수정 Worker: 실제 코드 변경
- 테스트 Worker: 자동 테스트 실행 및 실패 원인 분석
- 배포 Worker: 커밋/승인/푸시 상태 추적

### 5) 코드 수정
- 기존 파일 우선 수정
- 새 파일 생성은 필요한 경우에만 수행

### 6) 자동 테스트
- 단위 테스트 실행
- 실패 시 로그 수집
- 재수정 후 재실행

### 7) 커밋 및 배포 추적
- Git Commit 기록 저장
- 대표 승인 대기 상태 기록
- Git Push 가능 시 진행

## 상태 관리
각 작업은 다음 상태를 가진다.
- pending
- analyzing
- modifying
- testing
- waiting_approval
- waiting_permission
- committed
- pushed
- failed

## 산출물
- 개발 지시 해석 기록
- 분석 결과
- 수정 대상 목록
- 테스트 결과
- 커밋/승인/푸시 추적 기록

## 결론
본 Development Engine은 기존 Business AI OS 구조를 유지하면서, 대표의 개발 지시를 수정 중심 워크플로우로 실행 가능한 회의실 개발 운영 체계로 전환한다.
